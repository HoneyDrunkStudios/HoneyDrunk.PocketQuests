## Fixture inventory and isolation

- `SqlApiTests` creates `PocketQuests_Tests_<guid>` and its corresponding isolated Identity database for each test. Production DACPACs build/deploy the schemas; disposal deletes only the test's databases. Existing tests cover API restart, concurrent hosts (12 completion requests), operation payload mismatch, account isolation, rollback/audit behavior, offline recorded-time validation, penalties/streaks, schema upgrade/backfill and Undo.
- `CompletionLedgerSqlTests.cs` adds canonical reward-pool/receipt checks, selective Undo preserving another completion, no-op completion, stale Undo after recompletion, overall threshold changes and receipt replay after a new API host. These reuse the existing real-SQL fixture rather than adding a second persistence implementation.
- `BrowserFixture.cs` / `PocketQuests.BrowserHost` reuse that isolated SQL/Identity fixture. Initialization now sits inside the cleanup boundary so partial initialization also attempts disposal. The external OIDC provider and short-lived signing identity are test-only; product requests reach real API/SQL. `e2e/journey.mjs` injects a one-time save failure and drops one committed completion response to exercise recovery. Browser sign-in is **not** evidence of live-provider sign-in.
- Native cache/secure storage is real only on native builds. The web adapter intentionally uses in-memory session/cache maps. Its fresh-session journey proves SQL persistence by signing the same disposable identity in again; it cannot prove native encrypted-cache recovery across process death.

## Fast backend architecture feedback

Run `pwsh -NoProfile -File scripts/Test-BackendArchitecture.ps1` from the repository root. It restores locked package-mode dependencies, builds SchemaTests, then runs only compiled architecture and scoped-registration tests; it never opens a SQL connection. After a current Release build, use `-NoBuild` for the short feedback loop. The existing hosted backend lane runs the same command after its source-mode solution build, before SQL verification. A missing or empty test selection fails.

The five rules inspect the built product, including method-body references, nested generic/array shapes, constructor parameters and compiler-generated async/lambda types:

- Services cannot depend on EF types, shared persistence implementation types or any `DbContext` subclass; typed product Data interfaces and entities remain legitimate
- Contracts cannot depend on product Data or persistence types, even inside collection/task wrappers
- Types under `PocketQuests.Api.Endpoints` cannot call or reference Data, EF or Domain directly; Services owns business execution, while hosting/composition and lifecycle adapters retain their separate responsibilities
- Data cannot depend on public Contracts, including references hidden inside method bodies
- Domain cannot depend on outer product/shared layers, HTTP/persistence types or direct BCL file/network/reflection/process/environment/TimeProvider dependencies; pure BCL and NodaTime dependencies remain supported, including the existing `CommandDigest` in-memory `Stream`/`MemoryStream`/`SeekOrigin` serialization and Domain-owned compiler-generated static-data types

`ArchitectureBoundaryTests` applies these rules to real assemblies and proves each predicate against an intentionally invalid fixture and a valid counterpart. Additional cases cover an async Domain bypass, an EF factory, a context reference appearing only in a method body, generic constraints, catch-only EF exceptions, concrete EF repository ancestry and a persistence type hidden in a JSON attribute. The small BCL-only scanner fails on unresolvable references or unsupported IL operands; it does not silently skip them. There is no added architecture package or violation baseline.

These are static dependency boundaries, not proof of business correctness, mapping purity, runtime service-locator behavior or arbitrary effects reached through reflection/dynamic loading. SQL parity, HTTP compatibility, real browser/API/SQL journeys and native/provider acceptance remain separate required evidence; this fast command does not replace them.
